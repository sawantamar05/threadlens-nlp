# Portfolio materials

## LinkedIn project title

ThreadLens — NLP Discussion Intelligence

## LinkedIn description

Built an original local NLP application that categorizes technical discussion comments as analysis, requests, or commentary. ThreadLens combines a FastAPI service, Streamlit interface, SQLite annotation history, and reproducible scikit-learn/PyTorch workflows.

Collected 720 fresh public Hacker News comments from 36 discussions through the official API, preserving full source text locally. Created a frozen discussion-level train/validation/test split to prevent thread leakage. Compared majority-class and TF-IDF baselines with fine-tuned DistilBERT using three recorded training seeds. One validation-selected class-weighted-loss change raised mean test macro F1 from 0.278 to 0.488 against weak labels; the 0.65 goal was missed.

The application supports individual prediction, thread exploration, ordered CSV batches with safe exports, experiment charts, model metadata, and blind annotation review. Tests cover validation, leakage, provenance, metrics, reload behavior, and API/UI workflows.

Benchmark labels are generated by a local NLI model. Reported metrics measure provisional agreement with weak labels; independent semantic accuracy is unmeasured. AI assistance was used for implementation, testing, experiments, and documentation. Raw comments and model weights remain outside public Git.

## Two-minute demonstration

1. Start `threadlens serve`. Explain that the taxonomy categorizes contributions and does not verify factual truth. If using `--demo`, say clearly that the model and source examples are synthetic fixtures.
2. Paste an original supported claim, select a trained model, and classify. Show named scores, model version, and truncation/uncertainty warnings.
3. Upload `data/demo/comments.csv`, process it, and download results; show that original row order and columns are retained.
4. Analyze a public HN story with a small comment limit. Explain sampling bounds and the distinction between predictions and reviewed references.
5. Open Experiments; identify weak-label provenance before discussing the measured results and seed variation.
6. Open Annotation review in blind mode. Explain how a person's initial label differs from accepting AI suggestions. Any automated demo review uses AI-assisted provenance.

## Interview questions and answers

**Why three labels?** They describe contribution types rather than sentiment. A genuine primary request takes precedence; supported claims are analysis; remaining reactions and unsupported assertions are commentary. Mixed and rhetorical cases remain ambiguous.

**How do the API and interface share models?** Streamlit calls the loopback API. A process-local manager loads registered artifacts and reuses them, so the UI has no second neural-model copy or separate prediction logic.

**How did you avoid leakage?** Entire story groups belong to only one frozen partition. TF-IDF fits only on training text. Every method and seed uses those same rows, and validation controls selection.

**What do three seeds tell you?** They measure training randomness on fixed partitions. They do not provide three independent test datasets or estimate uncertainty from alternative story samples.

**Are the labels ground truth?** No. A local pretrained NLI teacher produces unreviewed weak labels. Agreement with them is provisional and can reproduce the teacher's errors. Independent human semantic validation remains unmeasured.

**Why keep a TF-IDF baseline?** It is fast, interpretable at the feature level, inexpensive, and establishes whether neural fine-tuning adds measured value. A transformer is not assumed superior before comparison.

**How is the improvement chosen?** Exactly one change is declared from training and validation evidence, recorded and committed before improved test evaluation. Original results and all seeds remain available; test performance does not trigger repeated searches.

**What happens to long comments?** Full cleaned source text remains locally stored. DistilBERT uses a bounded leading token window and reports truncation. Late requests or evidence can be missed. The weak-label teacher's overlapping windows introduce their own aggregation limitations.

**How is annotation history trustworthy?** Original drafts and immutable revisions are separate. Suggestion exposure is recorded; accepting an AI label is AI-assisted review. A frozen weak benchmark is not silently rewritten by later corrections.

**What would you do next?** Build an independently blind-labeled benchmark with multiple reviewers and adjudication, measure taxonomy agreement, evaluate calibration, and analyze domain and temporal shift before considering broader use.

**Was it independently authored?** This is an original personal portfolio project built with substantial Codex assistance. No course starter, annotations, datasets, checkpoints, or Git history were reused. Claims refer to implemented behavior and recorded evidence.
